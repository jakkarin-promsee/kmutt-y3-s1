1. **Phase 1 กับ 2 ไม่มีอันไหน "พัง"** — ด่านตายผ่านครบ, K5 ผ่าน, K7/K4/K13 ไม่ทริป, ราคาโปรเจกต์ประเมินได้ครั้งแรก

# 2 — ⭐⭐⭐ การวินิจฉัยกลาง: **อาการ 3 อย่างมีรากเดียว และรากนั้นแก้ได้เกือบฟรี**

นี่คือสิ่งที่ result ทั้งสองไฟล์**เห็นชิ้นส่วนครบแล้วแต่ไม่ได้ต่อกัน** และกุคิดว่ามันเปลี่ยนการอ่านผลทั้งหมด

## 2.1 สูตรที่หายไป

`sensor.py:80` เรนเดอร์ glimpse ทุกอันลง `G_fine` **คงที่** ไม่ว่า `s` จะเท่าไหร่ ⟹ วัตถุกว้าง `w` (สัดส่วนผ้าใบ) จะได้พิกเซลใน patch เท่ากับ

$$\text{detail}(s) = \min\Big(\underbrace{\tfrac{w}{s}\cdot G_{fine}}_{\text{จำกัดโดยการเรนเดอร์}},\ \underbrace{w\cdot W_{canvas}}_{\text{จำกัดโดยพิกเซลจริง}}\Big)$$

จุดตัดของสองเทอมอยู่ที่

$$\boxed{s^{*} = \dfrac{G_{fine}}{W_{canvas}}}$$

| ช่วง        | เกิดอะไร                                                                     | โมเดลควรทำอะไร                                |
| ----------- | ---------------------------------------------------------------------------- | --------------------------------------------- |
| $s < s^{*}$ | พื้นที่หด · **รายละเอียดคงที่** (เพราะเป็นการ**ขยายภาพ** ไม่ใช่การได้ข้อมูล) | ⛔ **ไม่มีเหตุผลจะไปเลย — แย่กว่าโดยเด็ดขาด** |
| $s > s^{*}$ | พื้นที่โต · **รายละเอียดหด**                                                 | ⭐ **นี่คือที่เดียวที่มี "การเลือก" ให้ทำ**   |

$$\Longrightarrow \textbf{ช่วง action ของ } s \textbf{ ที่มีความหมายจริง} = [s^{*},\ s_{max}] \quad \textbf{ไม่ใช่ } [s_{min}, s_{max}]$$

## 2.2 เอาสูตรนี้ไปทาบกับทุกอย่างที่รันมาแล้ว

| การทดลอง                          | $W_{canvas}$ | $G_{fine}$ | $s^{*}$      | ช่วง `s` ที่ตั้งไว้ | **ช่วงที่มีความหมายจริง**                 |
| --------------------------------- | ------------ | ---------- | ------------ | ------------------- | ----------------------------------------- |
| ⛔ **smoke T-MNIST (§2.6, §5.7)** | **60**       | 64         | ⛔ **1.067** | [0.15, 0.50]        | ⛔⛔ **ว่างเปล่า — ทั้งช่วงอยู่ใต้ `s*`** |
| ⛔ **Phase 2 arm A / cache**      | **224**      | (64)       | **0.286**    | [0.10, 0.35]        | ⚠ **[0.286, 0.35] = แคบมาก**              |
| ✅ ถ้าใช้ผ้าใบ 448                | 448          | 64         | **0.143**    | —                   | ✅ **[0.143, 0.30] = 2.1×**               |
| ✅ ถ้าใช้ผ้าใบ 640                | 640          | 64         | **0.100**    | —                   | ✅ **[0.10, 0.30] = 3×**                  |

## 2.3 ⟹ อาการทั้งสามอธิบายได้ด้วยแถวเดียว

### อาการ ก — "โมเดลเลือกที่จะไม่ซูม" (§5.7)

Phase 1 วัดได้ `mean s = 0.480` จากเพดาน `0.50` และ `Var_image[s] = 1.63e−4` แล้วเขียนว่า _"นี่คือ location collapse ในรูปของสเกล"_

⛔ **มันไม่ใช่ collapse — มันคือนโยบายที่ถูกต้อง** บนผ้าใบ 60 px ที่ `s* = 1.067` **ทุกค่าของ `s` เป็นการขยายภาพทั้งหมด** ⟹ แคบลง = ได้ข้อมูลน้อยลงโดยไม่ได้อะไรกลับมาเลย ⟹ **นโยบายที่ optimal คือกว้างสุดเสมอ และโมเดลก็หามันเจอ**

$$\Longrightarrow \textbf{ผลนี้ไม่ใช่หลักฐานว่าแกน } s \textbf{ เรียนไม่ได้ — มันคือหลักฐานว่าสนามซ้อมไม่มีแกน } s \textbf{ ให้เรียน}$$

### อาการ ข — "learned ไม่ชนะ random" (§5.7, 92.34 vs 92.78)

ถ้าแกน `s` ตายโดยการก่อสร้าง สิ่งที่เหลือให้ learned ชนะคือ `(x,y)` อย่างเดียว บนโจทย์ที่เลขกว้าง **0.467 ของผ้าใบ** + ช่องหยาบเห็นทั้งใบ + glimpse กว้างได้ถึง 0.50 ⟹ **มองมั่วก็เจอ** ตามที่ §5.7 ข้อ 3 เดาไว้เอง — และตอนนี้มีกลไกเชิงตัวเลขค้ำแล้ว ไม่ใช่แค่การเดา

### อาการ ค — ⛔ **"ภาพเต็มซื้อได้แค่ 1.3 จุด" (§6.1)**

นี่คือข้อที่หนักที่สุดใน Phase 2 และมันถูกวัดบน `cache.py:FULL=224`

`[วัดเอง — scratch]` เอา `cert.answer_coarse_px` ของทั้งเซลล์มาสเกล:

| ผ้าใบของ arm A                   | ขนาด answer (median) | ⭐ **% ของตัวอย่างที่ answer ≥ 32 px** (เกณฑ์ "จำแนกได้" ของรีโปเอง) |
| -------------------------------- | -------------------- | -------------------------------------------------------------------- |
| 64 (ภาพย่อ)                      | 8 px                 | 3.6%                                                                 |
| ⛔ **224 (ที่ Phase 2 ใช้จริง)** | **28 px**            | ⛔ **44.2%**                                                         |
| **448**                          | **56 px**            | ✅ **71.6%**                                                         |
| **640**                          | **80 px**            | ✅ **81.8%**                                                         |

$$\boxed{\textbf{arm A ที่ 224 px } \underline{\textbf{จำแนกวัตถุคำตอบไม่ได้ใน 56\% ของตัวอย่าง}} \textbf{ — โดยเกณฑ์ของรีโปเอง}}$$

⟹ ประโยค _"รายละเอียดทั้งก้อนมีมูลค่า 1.3 จุด"_ **ถูกวัดบน pipeline ที่รายละเอียดถูกทำลายไปก่อนแล้ว**
และ Phase 1 §5.4 **พิสูจน์ข้อนี้ไว้เองในไฟล์ข้างๆ กัน** — แค่ไม่มีใครเอาสองไฟล์มาวางทาบกัน

⚠ **ข้อจำกัดที่ต้องพูดคู่กันเสมอ:** นี่เป็น `[ARG]` ไม่ใช่ `[วัดเอง]` — มันบอกว่า _"เหตุผลที่ arm A ต่ำอาจเป็นเรื่องความละเอียด"_ **ไม่ได้บอกว่าเพิ่มความละเอียดแล้ว arm A จะขึ้น** เพราะ arm A **overfit ตั้งแต่ ep12 อยู่แล้ว** (§6.3) ⟹ อาจติดเพดานของ `n` ก่อนถึงเพดานของพิกเซล **⟹ ต้องวัดสองแกนพร้อมกัน ไม่ใช่แกนเดียว**

## 2.4 ของแถมของการวินิจฉัยนี้: **มันบอกวิธีตั้งค่าที่เหลือให้เลย**

| `W_canvas`    | 224 (Phase 2) / 640 (timing) | ⭐ **≥448**                    | ต่ำกว่านี้ **สมมติฐานหลักของโปรเจกต์เป็นเท็จโดยการก่อสร้าง**                                                                                                                |
| `G_fine`      | 64                           | **คง 64**                      | ⛔ **อย่าดัน G_fine ขึ้นเพื่อแก้ C3** — มันแพงแบบกำลังสองและมัน**ดัน `s*` ขึ้น = ฆ่าแกน `s` อีกรอบ** · ให้แก้ด้วย **ผ้าใบ** แทน ซึ่งราคาแค่ +15–32% `[วัดเอง Phase 1 §2.7]` |

⟹ **448 คือค่าที่ซื่อสัตย์ที่สุด** (71.6% และแทบไม่ขยายอะไร) · ถ้าอยากได้ 640 จริงๆ ต้อง **letterbox ไม่ใช่ stretch** ซึ่งเปลี่ยนพิกัด normalized ของ label ⟹ ต้องปั่นใหม่

# 3 — ⛔ ปัญหาที่รากข้างบน **อธิบายไม่ได้** — และนี่คือของจริง

## 3.1 ⛔⛔⛔ **prior ของคู่ category กินพื้นที่ที่เหลือเกือบหมดบน IID**

Phase 1 §3.2 วัด S2 (_"จำ argmax_c P(hop2=c | hop1b)"_) ไว้แค่ **train 0.237** กับ **comp-test 0.000** — **ช่องที่สำคัญที่สุดคือ IID-test และมันหายไป**

`[วัดเอง — scratch]` กุ reproduce `common.add_iid_split` เป๊ะ (seed 20260819 · majority ออกมา **0.1043** ตรงกับ Phase 2 ทุกหลัก ⟹ split ตรงกันแน่นอน):

| นโยบาย                                                                 | train  | ⭐ **IID-test** | comp-test |
| ---------------------------------------------------------------------- | ------ | --------------- | --------- |
| **S2 — lookup ล้วน (ให้ category ของ anchor ฟรี ไม่ต้องมองพิกเซลเลย)** | 0.2140 | ⛔ **0.1972**   | 0.0000    |
| พื้น majority                                                          | —      | 0.1043          | 0.0344    |
| **arm A ภาพเต็ม 224 (GAP)**                                            | —      | **0.2153**      | 0.0362    |
| arm A + mixer                                                          | —      | 0.2077          | 0.0424    |
| ภาพย่อ 64px                                                            | —      | 0.2020          | 0.0375    |

$$\boxed{\textbf{ตารางความจำ } \underline{\textbf{ที่ไม่มองภาพเลย}} \textbf{ ได้ } \mathbf{0.197} \textbf{ · arm A ที่เห็นทุกพิกเซลได้ } \mathbf{0.215}}$$

`[วัดเอง — scratch]` เสริม: `H(hop2) = 5.792` bits · `H(hop2|hop1b) = 4.309` bits ⟹ **แค่รู้ชนิดของ anchor ก็ได้ข้อมูลไปแล้ว 1.48 bits (26%)** · คู่ (anchor, answer) ที่ต่างกันมี 1,395 คู่ แต่ **top-100 คู่กิน 53.4% ของทั้งเซ็ต** · และบน IID-test มีแค่ **6.8%** ของแถวที่คู่ของมันไม่เคยโผล่ใน train

| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ⛔ **มองร้าย** | S2 = 0.197 ≈ arm A = 0.215 ⟹ **แถบที่การมองภาพซื้อได้จริงกว้างแค่ ~1.8 จุด** ⟹ C−B ต้องอยู่ในนั้น ขณะที่ **ความแปรปรวนระหว่างรัน ≈ 1 จุด** (§3.1 ของ Phase 2) ⟹ **K1 วัดไม่ได้**        |

$$\Longrightarrow \textbf{การวัดที่ตัดสินข้อนี้ยังไม่เคยทำ และมันถูกมาก}$$

**การวัดนั้นคือ:** รัน arm A ซ้ำหนึ่งครั้งโดย**บันทึกคำทำนายรายตัวอย่าง** แล้วแยก accuracy ตาม _ความถี่ของคู่ (anchor, answer) ใน train_ — ถ้า arm A ถูกเฉพาะคู่ที่พบบ่อย **แปลว่ามันคือ prior** · ถ้ามันกระจายสม่ำเสมอ **แปลว่ามันมอง** · ราคา ≈ **25 นาที GPU + 20 บรรทัด**

## 3.2 ⛔⛔ **compositional split ไม่มีหัวเรื่องให้อะไรโผล่**

arm A 0.0362 เทียบพื้น 0.0344 ⟹ **เหนือพื้น 0.2 จุด** ⟹ ถ้ารัน Phase 5 บน split นี้ **ทุก arm จะกองอยู่ที่พื้น และ C−B อ่านไม่ได้**

⭐ **แต่ข้อนี้กับ §3.1 เป็นข้อเดียวกันมองคนละด้าน:** split เชิงประกอบ **ฆ่า prior โดยการก่อสร้าง (S2 = 0.000 เป๊ะ)** ⟹ พอเอา prior ออก **ไม่มีอะไรเหลือเลย** ⟹ นั่นแปลว่า _ทุกอย่างที่ arm A ทำได้บน IID มาจาก prior_ — ซึ่งเป็นการอ่านที่ **มองร้าย** ข้างบน

⚠ **ยกเว้นว่า** ผ้าใบ 224 ทำให้มันมองไม่ออกอยู่แล้ว (§2.3) ⟹ **สองสมมติฐานนี้แยกกันไม่ออกจนกว่าจะวัดที่ 448**

# 6 — ❓ ที่กุอยากให้มึงตัดสิน / ที่กุยังไม่ชัวร์

1. **ผ้าใบ** — เอา 448 (ซื่อสัตย์) หรือ 640 (ตัวเลขสวยกว่าแต่ 52% ของภาพโดนขยายแกนตั้ง)? และให้กุรัน **M1** เลยมั้ย (ภาพอยู่บนดิสก์ครบแล้ว, ~3 ชม.)

2. **กุตีความ §5.7 ใหม่ว่า "ไม่ใช่ scale collapse แต่เป็นสนามซ้อมที่ไม่มีแกน `s`" — มึงเห็นด้วยกับการอ่านนี้มั้ย** เพราะถ้าเห็นด้วย มันเปลี่ยนสถานะของ §5.7 จาก _"สัญญาณอันตรายของกลไก"_ เป็น _"bug ของการตั้งค่า"_ และกุอยากให้มึงยืนยันก่อนกุเขียนลง `progress.md`

3. **`min_sep` เป็น Chebyshev + `s_max` = 0.30** — ยอมจ่าย yield ลงเหลือ ~7–9k เพื่อได้การรับประกันเกณฑ์ 10 กลับมามั้ย? (มึงเคยบอกเองว่า _"วัดสูงกว่า 0.25 จะตีผลยาก"_ — Chebyshev 0.30 **ไม่ใช่** Euclidean 0.30 นะ มันเข้มกว่า ⟹ อยากให้มึงยืนยันว่านับเป็นคนละเรื่อง)

4. **สนามซ้อม** — `ideas-choose.md` §10 เขียนว่า **2-digit** แต่ Phase 1 ทำ 1-digit · จะให้สร้างใหม่ตามสเปก + ประกาศเกณฑ์เข้าใช้ หรือจะยอมให้สนามซ้อมทำหน้าที่แค่ _"โค้ดไม่พัง"_ แล้วย้ายการเลือกยาไปสนามจริง (แพงกว่ามาก)?

5. **`answer_margin` 1.17** — อันนี้กุกังวลที่สุดในบรรดาปัญหาชั้นรอง เพราะมันเป็นเพดานที่**ยกไม่ได้ด้วยลูกบิดใดๆ** และเราถูกล็อกไม่ให้ใช้ margin filter (มันทำให้ทางลัดแรงขึ้น) · มึงอยากให้กุไปสำรวจ **"ใกล้ = ระยะขอบกล่อง แทน ระยะ centroid"** มั้ย หรือถือว่าเป็นเพดานที่ยอมรับแล้วรายงาน?

6. เรื่องที่กุ **ไม่แน่ใจจริงๆ**: กุอ่าน §6.1 ว่าเป็น artifact ของความละเอียด แต่ **arm A overfit ตั้งแต่ ep12** เป็นข้อเท็จจริงที่ทานการอ่านนั้น — ถ้าโมเดลจำ train ได้หมดแล้ว การให้พิกเซลเพิ่มอาจไม่ช่วยเลย · กุเลย**ไม่กล้าฟันธง** และเสนอ M1 กับ M2 ให้รันคู่กันเสมอ · ถ้ามึงมีมุมที่กุมองไม่เห็นตรงนี้ อยากฟัง
